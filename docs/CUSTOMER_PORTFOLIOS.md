# Admin customer portfolios — implementation and verification

Admin **Customers** now opens **Employees & Customer Portfolios**. Navigation is Customers → Employee → Assigned Customers → existing Customer Details → Loans / KYC / Installments / Payments. All Customers and Unassigned Customers remain separate global views.

## Features

- Genuine global totals: employees, customers, assigned/unassigned customers, active customers, distinct customers with open loans.
- Employee directory: prefix search by name/code/mobile; branch/status filters; name/customer-count/outstanding sorts; pagination; employees with zero customers remain visible.
- Employee customer portfolios and global views: paginated search, status/KYC/loan filters, deterministic sorting, loan/outstanding/overdue summaries and last actual received-payment date. An approved KYC snapshot remains approved while a revision is under review.
- Eight existing-customer detail sections: Overview; Personal & Contact; Approved KYC & Documents; Loan Accounts; Installment Schedule; Payments & Collections; Overdue & Advance; Timeline & Audit.
- Detail sections load on demand and paginate independently. Existing loan, KYC, receipt/print, edit and issuance screens are linked. Customer activation/deactivation remains available in Customer Details using the existing status endpoint.
- Small screens use employee/customer cards and wrapped tabs. Larger customer tables use a controlled scrolling region. Core actions have at least 44px height.
- Missing, null and dangling employee assignments appear under Unassigned Customers; no ownership is fabricated.

## Ownership and financial integrity

The existing customer profile owner is `Customer.employeeId`. A loan separately retains `Loan.employeeId` as its servicing employee and `Loan.createdBy` as its original issuer. Collections and settlement positions retain collector/custody attribution.

Reassignment requires an active authenticated Admin, an existing active destination employee, the expected previous employee ID and a reason of 5–1000 characters. The effective timestamp is generated by the server. A database transaction updates only the customer profile owner/branch, linked KYC assignment and their version fields, then writes an AuditLog and CustomerTimeline entry. The customer's residential city, area and address are preserved. Stale/repeated assignments return HTTP 409. Existing loans, schedules, receipts, payments, receiving accounts and custody records are never rewritten by reassignment.

This is **profile/KYC reassignment**, not a transfer of existing loan servicing. The form and details explain that distinction. The old profile owner loses customer/KYC access; the new owner gains it. Existing loan servicing permissions continue to follow the loan's existing employee. Portfolio totals follow the current customer owner; collector-based reports keep their original attribution.

New endpoints require ADMIN role and an active Admin record. Anonymous requests receive 401, Employee requests receive 403. Customer lists explicitly project safe operational fields; Aadhaar/PAN, identity numbers, encrypted KYC data and document contents are excluded. Approved KYC documents continue through the existing authenticated KYC workflow. Audit responses omit raw old/new values that could contain sensitive KYC data.

No schema fields or data migration were required. Additive indexes support owner/name order, case-insensitive prefix name/code/mobile search, employee branch/status/name order, customer loans, loan due dates, latest customer receipts and customer audit/timeline history. Existing indexes are preserved.

## Routes

Frontend:

| Path | Purpose |
| --- | --- |
| `/admin/customers` | Employee directory, default Customers landing page |
| `/admin/customers/all` | Global customer search |
| `/admin/customers/unassigned` | Unassigned customers |
| `/admin/customers/employees/:employeeId` | Assigned customer portfolio |
| `/admin/customers/:id` | Existing customer detail route, expanded to eight sections |

New backend routes, all under `/api/v1/customer-portfolios`:

| Method / relative path | Purpose |
| --- | --- |
| `GET /` | Directory, summary, branches and pagination metadata |
| `GET /employees/options` | Paginated active employees for reassignment |
| `GET /employees/:employeeId` | Filtered, paginated customer portfolio |
| `GET /customers` | All/unassigned customer queries |
| `GET /customers/:id` | Safe overview and calculated summaries |
| `GET /customers/:id/loans` | Paginated loans with the existing schedule-summary calculation |
| `GET /customers/:id/installments` | Paginated existing installment query; ALL/TODAY/OVERDUE/UPCOMING |
| `GET /customers/:id/payments` | Actual receipt dates, original entry timestamps and existing allocation timing |
| `GET /customers/:id/history` | Paginated customer timeline and sanitized customer/KYC audit events |
| `PATCH /customers/:id/assignment` | Controlled audited profile/KYC reassignment |

The legacy customer list endpoint now uses a safe field projection. Legacy approved customer-request detail authorization follows the current profile owner after reassignment. Existing financial APIs and their calculations are unchanged.

List query parameters: `page`, `limit` (1–100), `search` (literal case-insensitive prefix, max 100 characters), `sort`, `direction`. Directory supports `branchId`/`status`; customer lists support `status`, `kycStatus`, `loanState`, `city`, `area`, `assignment=all|unassigned`. Sort fields are whitelisted. Page/search/filter state is kept in the URL and search is debounced 350ms.

## Scale and query verification

The integration suite creates **1,000 synthetic customers** in an isolated local MongoMemoryReplSet, including one employee with 650 customers, another with 340, a zero-customer employee, an inactive employee and 10 legacy unassigned/orphaned customers. No fixtures connect to Atlas.

Ordinary name/code customer pages apply indexed ordering and pagination before financial/KYC/document metadata lookups. Full KYC documents are never loaded for lists. Only predicates/sorts that need calculated fields perform early enrichment; KYC filtering does not calculate every customer's balances. Related data are gathered by server-side aggregation, not one HTTP request or one application database query per customer. Loan sections load schedules in one batch for that loan page. `explain('executionStats')` verifies the owner/name compound index and exactly 20 customer documents and 20 index keys examined for a 20-row indexed page. MongoDB reported 1ms execution time for that indexed query.

Measured local HTTP request times from the dedicated 1,000-customer verification run (single samples, includes authorization and serialization, not production latency promises):

| Request | Time |
| --- | ---: |
| Employee directory with global summary | 740ms |
| Employee portfolio, first 50 customers | 181ms |
| Employee portfolio, second 50 customers | 154ms |
| Customer mobile-prefix search | 37ms |
| All Customers first page | 55ms |
| Unassigned Customers | 286ms |
| Active-loan filter with outstanding sort | 824ms |
| Overdue customer filter | 785ms |
| Approved-KYC filter | 262ms |

Raw measurements: `tmp/financial-audit/portfolio-performance.json`. Subsequent full-suite runs may replace that generated file with their own timing samples. Aggregated financial sorts/counts still need to inspect all matching customers' recorded finances on the server; 10,000+ customer production-like load has not been benchmarked. No cached financial totals or competing balance formulas were introduced.

## Configured Atlas data comparison

Read-only raw-BSON fingerprints were taken before and after the work for all 22 collections in `loan_management`. **19 collections matched exactly**, including customers, KYC, loans, schedules, collections/payments, employees, Admins and receiving accounts.

The comparison detected concurrent activity in `collectionpositions`, `employeesettlements` and `auditlogs`: an existing Admin `SETTLEMENT_REVERSED` event at **2026-10-26 17:33:16 UTC**, followed by three `FINANCIAL_PROOF_VIEWED` events. The settlement/position counts stayed at one each; audit entries increased by four. These actions were not performed by the portfolio verification, whose browser and test writes used disposable local databases. They were left untouched. Consequently an assertion that the entire configured database stayed unchanged would be inaccurate.

Evidence is in ignored local files `tmp/financial-audit/portfolio-records-before.json` and `portfolio-records-after.json`; the investigation prints only action types, roles and timestamps, never customer/account details. No reset, deletion, real-data fixture seeding or financial record repair was performed.

## Manual acceptance

1. Open `http://127.0.0.1:5173/admin/login` and sign in with your existing Admin account.
2. Open **Customers**. Confirm **Employees & Customer Portfolios** is the first screen. Check summary counts against your records.
3. Search an employee by the start of their name, code or mobile; filter branch/status, change sort and open **View Customers**.
4. Search/filter/page their portfolio. Open **View Details** and exercise all eight sections and the existing KYC, loan and receipt links.
5. Use **All Customers** for global oversight and **Unassigned Customers** for incomplete legacy assignments.
6. If a real test reassignment is desired, open **Reassign Customer**, choose an active employee and enter a reason. Confirm the new profile owner and timeline; check old/new Employee access. Existing loan servicing and collector/custody attribution should stay as shown on their original records.
7. On an Android browser, verify cards, buttons and hamburger navigation without zooming; test portrait and landscape and a slower connection.
